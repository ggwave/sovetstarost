# Настройка Firebase для CRM Совета обучающихся

Проект: **`sovet-701c5`**  
Авторизация: **Firebase Authentication — Email/Password**  
База: **Cloud Firestore**

## 1. Authentication

1. Firebase Console → выбери `sovet-701c5`.
2. Authentication → Sign-in method → включи **Email/Password**.
3. Не включай Anonymous, Phone или сторонние провайдеры — проекту нужен обычный email/password.
4. В Authentication → Settings → Authorized domains проверь домен публикации сайта. Добавь `localhost` для локального теста.

Самостоятельной регистрации на сайте нет. Firebase Auth-пользователей сначала создаёт председатель через Console → Authentication → Users → Add user.

## 2. Firestore и первый председатель

1. При необходимости создай Cloud Firestore в проекте.
2. Authentication → Users → Add user: создай почту и пароль председателя.
3. Скопируй UID пользователя.
4. Firestore → Data → Start collection → `users`.
5. Укажи Document ID точно как UID из Authentication.
6. Добавь поля:

| Поле | Тип | Значение |
|---|---|---|
| `name` | string | Имя и фамилия председателя |
| `email` | string | Та же почта, что в Auth |
| `role` | string | `chair` |
| `sectorId` | string | `administrative` |
| `active` | boolean | `true` |
| `createdAt` | timestamp | Текущие дата и время |
| `showOnSite` | boolean | `false` (необязательно; публикацию можно включить позднее) |

Этот шаг делается вручную, потому что до первого председателя некому выдать право создавать профили из CRM.

## 3. Публикация Firestore Rules

1. Открой Firebase Console → проект `sovet-701c5` → Firestore Database → Rules.
2. Используй именно файл **`firestore.rules` из корня репозитория**: https://github.com/ggwave/sovetstarost/blob/main/firestore.rules.
3. Полностью замени содержимое редактора правилами из этого файла.
4. Нажми **Publish** и дождись подтверждения публикации.

Файлы `firestore.rules.example` и `js/firestore.rules.example` синхронизированы с основным файлом. Не используй сохранённую локальную копию старой версии.

Правила разрешают конкретные рабочие коллекции и запрещают остальные пути по умолчанию. Публично доступны только опубликованные новости, собрания, проекты, документы, планы секторов и отдельная обезличенная витрина `publicTeam`. Для статуса обращения разрешён только точечный `get` документа `initiativeTracking/{trackingId}`; список таких документов читать нельзя. Полные обращения `initiatives` публично не читаются.

## 4. Добавление остальных участников

1. Authentication → Users → Add user: создай аккаунт с почтой и временным паролем.
2. Скопируй UID.
3. Войди как председатель и открой CRM → Участники.
4. Заполни UID, email, имя, роль и сектор; нажми «Сохранить профиль».
5. Передай ученику email и пароль безопасным способом. Пароль не вводится в CRM и не хранится в Firestore.

Основные роли:

| `role` | Сектор |
|---|---|
| `chair` | `administrative` автоматически |
| `deputy_chair` | `administrative` автоматически |
| `secretary` | `administrative` автоматически |
| `administrative` | `administrative` автоматически |
| `sector_lead` | `information`, `culture`, `social`, `study` или `sport` |
| `member` | Один из пяти рабочих секторов либо пустая строка |

Только председатель может редактировать роли, сектора и активность других профилей. Административный сектор может координировать проекты, инициативы, планы и отчёты, но не управляет списком аккаунтов.

## 5. Основные коллекции

- `users`
- `initiatives`
- `initiativeTracking`
- `activityFeed`
- `meetings`
- `polls` и подколлекция `polls/{pollId}/votes/{uid}`
- `tasks`
- `decisions`
- `announcements`
- `documents`
- `projects`
- `sectorPlans`
- `publicTeam` (отдельные карточки с именем, ролью и сектором; без email и контактов)
- `sectorReports`

Все схемы и допустимые поля проверяются Firestore Rules. Если вручную создавать записи в Console для теста, используйте поля и типы, предусмотренные `app.js` и правилами.

## 6. Проверка после настройки

1. Войти под председателем: должен открыться обзор CRM.
2. Убедиться, что он отображается в административном секторе.
3. Создать пользователя в Authentication, затем добавить профиль через «Участники».
4. Проверить роли `deputy_chair`, `secretary`, `administrative` — они должны получать `sectorId=administrative` автоматически.
5. В списке участников включить «Показывать на сайте» только для согласившихся участников; проверить, что публичная карточка не содержит почту и контакт.
6. В административном секторе создать собрание и голосование; они должны появиться в ленте событий, а у вошедших участников — во всплывающем уведомлении.
7. Отправить инициативу в публичной части без входа. После отправки сохранить ID и ссылку; проверить статус через форму отслеживания.
8. Изменить статус инициативы в CRM и проверить, что публичная карточка статуса обновилась.
9. Создать задачу, назначить исполнителя и проверить, что исполнитель может изменить её статус.
10. Создать отчёт от руководителя сектора и проверить сценарии «Принять» и «На доработку».
11. Проверить доступ под обычным участником и руководителем сектора, чтобы убедиться, что им недоступны административные функции.

## 7. Ограничения и важные замечания

- Всплывающие уведомления работают только пока пользователь авторизован и сайт открыт. Firebase Cloud Messaging (push в закрытом браузере) не включён.
- Голосования не анонимны: документы голосов привязаны к UID участника и доступны для подсчёта результатов в CRM.
- В модуле документов поддерживаются URL и текст. Загрузка файлов требует Firebase Storage и отдельных Storage Rules.
- Публичная форма инициатив не использует App Check/CAPTCHA и серверный rate limit. Для открытого школьного проекта соблюдай минимизацию публикуемых данных и следи за спамом.
- Публикация ZIP не меняет Firebase или GitHub Pages автоматически. Rules и сайт нужно применить отдельно.
